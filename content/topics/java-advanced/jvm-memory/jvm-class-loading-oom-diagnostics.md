## Overview

Two failures send Java developers to the JVM internals: a class that cannot be found (or the wrong version of it is found), and an `OutOfMemoryError`. Both look like application bugs, and both are usually platform problems — the classpath, the classloader hierarchy, or the memory the application is retaining.

This topic covers the loading side first, because classloader problems explain the strangest errors in Java, and the diagnosis side second, because each `OutOfMemoryError` message names a different resource, and each one has a different fix. Raising `-Xmx` is the right fix for exactly one of them.

## Theory

### Class loaders and parent delegation

Classes are loaded on demand by class loaders, in a hierarchy:

- **Bootstrap loader:** loads the JDK's own classes (`java.lang.*`). It is implemented natively, not in Java.
- **Platform loader:** loads JDK extension and platform classes.
- **Application loader:** loads classes from the classpath — your code and your dependencies.
- **Custom loaders:** created by frameworks and containers — web applications, application servers, and plugin systems each give their components their own loader, so two web apps can load different versions of the same library without interfering.

Loading follows **parent delegation**: a loader asks its parent first, and only loads the class itself if no parent has it. That is why your class cannot shadow `java.lang.String` — the bootstrap loader already has it — and why a class is identified by its name *plus* its loader: the same class loaded by two loaders is two different types, and casting between them throws `ClassCastException` even though the names match.

### Loading, linking, initialization

Loading a class runs through three phases: **loading** (read the bytecode and create the `Class` object), **linking** — verification (the bytecode verifier checks type safety), preparation (memory for static fields), and resolution (symbolic references to other classes are resolved) — and **initialization** (static initializers run, in source order). Most of this happens lazily: a class is loaded when it is first used, and initialized when it is first actively used.

### The classloading error family

- **`ClassNotFoundException`:** a class was requested by name (reflection, `Class.forName`, a service loader) and no loader could find it. Usually a missing dependency.
- **`NoClassDefFoundError`:** the class existed at compile time but is missing at runtime — a dependency that was present when the code was built and absent when it runs, or a class whose static initializer failed earlier. The "Def" is the giveaway: the definition was there when the code was compiled.
- **`NoSuchMethodError` / `IncompatibleClassChangeError`:** the class was found, but it is a different version than the code was compiled against — the classic symptom of two versions of a library on the classpath, where the loader found the older one first.
- **`LinkageError` / `ClassCastException` for the same class name:** the same class loaded by two different loaders.

The fix is almost always classpath hygiene: one version of each library, in the order you intend, and an understanding of which loader your framework uses.

### OutOfMemoryError: read the message

`OutOfMemoryError` is not one failure. The message names the exhausted resource:

- **`Java heap space`:** the heap is full of live (reachable) objects. Either the application genuinely needs more heap, or it is retaining objects it no longer needs — the retention leak covered in the garbage collection topic. Raising `-Xmx` helps only the first case; in the second it delays the same crash.
- **`GC overhead limit exceeded`:** the GC is spending more than 98% of its time collecting and recovering less than 2% of the heap. The heap is effectively full of live data; the fix is the same as for heap space — find what is retained.
- **`Metaspace`:** class metadata is exhausted. Usual causes are classloader leaks (a loader that cannot be collected because something still references it — a static map, a `ThreadLocal`, a JDBC driver registered in a shared registry) or code that generates classes without bound (dynamic proxies, generated bytecode).
- **`Unable to create new native thread`:** the operating system cannot create another thread — usually too many threads, each consuming a stack, rather than too little heap. Raising `-Xmx` makes this worse, because it leaves less memory for thread stacks.
- **`Direct buffer memory`:** off-heap direct buffers (NIO) exhausted their limit, set by `-XX:MaxDirectMemorySize`.

### Diagnosing: heap dumps, histograms, and logs

- **`-XX:+HeapDumpOnOutOfMemoryError` with `-XX:HeapDumpPath=`:** writes a heap dump (`.hprof`) automatically when the error occurs. Diagnose from the dump, not from a restart — the evidence is in the heap at the moment of failure.
- **`jcmd <pid> GC.heap_dump <file>`:** takes a dump from a running JVM without waiting for a crash.
- **`jmap -histo <pid>`:** a histogram of classes by instance count and memory — the fastest way to see what is filling the heap (a million `String` instances, a `HashMap` with ten million entries).
- **A heap analyzer (Eclipse MAT, VisualVM, YourKit):** open the dump, look at the dominator tree — which objects keep the most memory alive — and the path to GC roots for the biggest retainers. The leak is usually one collection holding references the application forgot.
- **GC logs (`-Xlog:gc*`):** show whether the heap is growing steadily (a leak), spiking (a workload burst), or full of long-lived data after every full GC.
- **`jstack <pid>`:** thread dumps for the native-thread case — count the threads and find what created them.

The diagnostic order is: read the message, reproduce with a dump, find the biggest retainer, then fix the retention — not the heap size.

## Key Concepts

- **Parent delegation:** a loader asks its parent first; a class is identified by name plus loader.
- **Loading, linking, initialization:** verification, preparation, resolution, then static initializers.
- **ClassNotFoundException vs NoClassDefFoundError:** missing by name vs missing at runtime after compiling against it.
- **Metaspace OOM:** class metadata — classloader leaks or unbounded class generation.
- **Heap dump + dominator tree:** the evidence for a retention leak; `-XX:+HeapDumpOnOutOfMemoryError` captures it automatically.

## Code Examples

### Two loaders, one class name, a ClassCastException

```java
// Two web applications each load their own copy of com.example.Config.
// Even though the class name is identical, the JVM treats them as
// different types, because identity is (class name, defining loader).
Object config = appOneLoader.loadClass("com.example.Config")
    .getDeclaredConstructor().newInstance();
com.example.Config typed = (com.example.Config) config; // ClassCastException
```

Explanation: the cast fails not because the class is wrong, but because the object was defined by `appOneLoader` while the cast refers to the copy defined by the application's own loader. The fix is to share the class through a common parent loader, or to communicate through an interface loaded by that parent.

### Capturing a heap dump automatically

```bash
java -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/dumps/ \
     -Xlog:gc*:file=/var/logs/gc.log \
     -jar app.jar
```

Explanation: when the JVM runs out of memory, it writes a dump to `/var/dumps/` before exiting, and the GC log records the heap's growth over time. The dump answers "what was retained"; the log answers "was it growing steadily or spiking". Both are needed — a dump alone cannot tell a leak from a burst.

### A classloader leak in miniature

```java
public class LeakDemo {
    // A static map in a class loaded by the application loader holds
    // instances of classes loaded by a child (web-app) loader.
    // The child loader can never be collected while the map holds them,
    // so redeploying the web app leaks a whole loader — and every class
    // it loaded — on each redeploy.
    private static final java.util.Map<String, Object> REGISTRY =
        new java.util.HashMap<>();

    public static void register(String key, Object value) {
        REGISTRY.put(key, value);
    }
}
```

Explanation: the map is reachable from a GC root (a static field), so everything it references is retained forever — including the classloader that defined those objects' classes, and therefore every class that loader loaded. The fix is to remove entries on undeploy, or to hold them with weak references.

## Best Practices

- Capture heap dumps automatically (`-XX:+HeapDumpOnOutOfMemoryError`); never diagnose an OOM from a restart alone.
- Read the OOM message before acting — each message names a different resource and a different fix.
- Keep one version of each library on the classpath, and know which loader your framework uses.
- Deregister drivers, listeners, and `ThreadLocal` values when a component (a web app, a plugin) is undeployed.
- Treat `-Xmx` as a sizing decision made from measurements, not as the first response to an OOM.

## Common Mistakes

- Raising `-Xmx` for a retention leak, a Metaspace leak, or a native-thread exhaustion — it helps none of them and can make the last one worse.
- Restarting after an OOM without a heap dump, destroying the only evidence.
- Putting two versions of a library on the classpath and debugging the resulting `NoSuchMethodError` as an application bug.
- Casting between two copies of the same class loaded by different loaders and reading the `ClassCastException` as a type error.
- Assuming `OutOfMemoryError` always means "not enough heap".

## Interview Importance

Class loading and OOM diagnosis are senior JVM topics: interviewers ask how parent delegation works, why the same class name can throw `ClassCastException`, and — most commonly — "your service throws `OutOfMemoryError: Java heap space` in production; what do you do?" The expected answer is a diagnostic sequence (dump, histogram, dominator tree, retainer), not "increase the heap".

## Interview Questions

- **Why can two classes with the same name be different types in one JVM?** Because class identity is the name plus the defining classloader; parent delegation exists precisely to prevent accidental duplication.
- **What is the difference between ClassNotFoundException and NoClassDefFoundError?** The first is a lookup by name that failed; the second means the class was present at compile time but missing at runtime.
- **Your service throws OutOfMemoryError: Metaspace. What do you check?** Classloader leaks (static references, ThreadLocal values, registered drivers) and unbounded class generation — not the heap size.

## Revision Summary

- Loaders form a hierarchy (bootstrap, platform, application, custom) with parent delegation; identity is name + loader.
- Loading → linking (verify, prepare, resolve) → initialization (static initializers run).
- `ClassNotFoundException` = not found by name; `NoClassDefFoundError` = present at compile time, absent at runtime; version skew gives `NoSuchMethodError`.
- Read the OOM message: heap space, GC overhead, Metaspace, native thread, direct buffer — each has a different fix.
- Diagnose with `-XX:+HeapDumpOnOutOfMemoryError`, `jmap -histo`, and a heap analyzer's dominator tree; fix retention, not heap size.
